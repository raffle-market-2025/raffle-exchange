# Приёмка обмена USDT и UAH и аудит ТЗ

Версия 1.3 • 28 октября 2026. Это план проверок будущей реализации и результат проверки согласованности документов. Это не отчёт об уже работающем обменнике.

## 1 Обязательные результаты

AC-001. Клиент покупает USDT за UAH: подтверждены гривневое зачисление в Ощад, выдача USDT в проверенном веб-процессе Walt, точное соответствие котировке и закрытие учёта.

AC-002. Клиент продаёт USDT за UAH: подтверждены USDT и выплата UAH через фактический кабинет Ощад, получатель и сумма соответствуют условиям, нет повторной выплаты.

AC-003. Перезапуск, повторный webhook и повторная команда не создают второй денежный эффект.

AC-004. Промо обрабатывается после каждой COMPLETED-сделки; сообщение отправляется через собственный разрешённый канал при наличии согласия. Отсутствующий канал фиксируется как пропуск, не обходится рассылкой в Walt.

AC-005. Входящие, исходящие, комиссии, резервы и остатки сходятся. Ни одна сумма неизвестного происхождения не помечается доходом автоматически.

AC-006. Полный автомат принимается по реально проверенному веб-процессу Walt и исполнению через Ощад. Отдельный торговый API не требуется. Обязательные CAPTCHA/2FA/личная подпись и неопределённые исходы сохраняются как остановки или assisted-этапы.

## 2 Пакет доказательств

Для каждого сценария: версия кода, настройки без секретов, входные условия, внутренний orderId, внешние идентификаторы, лента событий, результаты проверки получателя/суммы, ledger journals, состояние резервов, результат сверки и фактический исход. Для UI дополнительно размер экрана, язык и снимок с обезличенными данными.

Доказательства локальной модели маркируются `model`; записанные провайдерские события — `replay`; чтение рабочих аккаунтов — `production_read_only`; реальные переводы — `live`. Успешный mock не считается доказательством исполнения у Walt или Ощад.

## 3 Возможности и подключения

C-01. Рыночный ключ Walt сам не выполняет сделок; при отдельно проверенном веб-исполнителе торговые действия доступны только через его доменную очередь, без фиктивных trading endpoints.

C-02. В конфигурации USDT/UAH нет выбранного метода Ощад: предложение недоступно с понятной причиной.

C-03. Попытка отправить USD, USDC, RUB, другой актив или обратный порядок полей при заданном направлении отклоняется.

C-04. 401/403 отключает конкретный ключ; секрет не появляется в логах. 429 даёт backoff. HTTP 200 с бизнес-ошибкой не становится успехом.

C-05. Неизвестный base URL и redirect на иной host блокируются без передачи ключа.

C-06. BUY/SELL рыночного API сопоставлены с проверенными реальными объявлениями; клиентское направление не перевёрнуто.

C-07. Не подтверждён собственный торговый ID контрагента: нельзя импортировать чужую сделку в клиентскую историю.

C-08. Отзыв полномочий в процессе блокирует новые опасные команды; сверка уже отправленного продолжается.

## 4 Котировки и деньги

Q-01. Ввод суммы UAH и ввод суммы USDT дают согласованные прямой/обратный расчёты.

Q-02. Минимум, максимум, границы и шаг дробности проверяются на сервере; значения вне границ отклоняются без резерва.

Q-03. Нулевая, отрицательная, чрезмерно большая, NaN-подобная, экспоненциальная и неоднозначная локализованная сумма не превращаются в платёж.

Q-04. Запятая и точка на разных языках нормализуются однозначно; тысячный разделитель не интерпретируется как десятичный.

Q-05. Нулевая/отдельная/включённая комиссия рассчитана без двойного удержания; gross и net соответствуют направлению и валюте комиссии.

Q-06. Смена тарифа во время TTL не меняет уже принятую котировку. Истёкшая котировка не принимается заново.

Q-07. Два клиента одновременно принимают последние доступные средства: проходит только обеспеченное число сделок; остаток не отрицательный.

Q-08. Резерв истёк до принятия: новый резерв/новая котировка либо отказ. Оплаченный заказ не освобождается просто по TTL котировки.

Q-09. Устаревшие объявления и пустой рынок блокируют новые индикативные расчёты согласно policy; принятые обязательства сохраняются.

Q-10. Разница округления отражена в учёте и не уменьшает скрыто обещанный net.

## 5 Клиент покупает USDT

B-01. Штатный путь: один заказ, один входящий UAH, один release USDT, одно закрытие.

B-02. Клиент нажал «Оплачено», но Ощад не подтвердил зачисление: выдачи USDT нет.

B-03. Поддельная квитанция или текст об оплате не вызывает INBOUND_VERIFIED.

B-04. Входящий платёж меньше необходимого: исключение; частичная выдача не происходит самопроизвольно.

B-05. Переплата: согласованный обмен и отдельное обязательство по разнице; лишние UAH не исчезают из учёта.

B-06. Платёж от иной стороны/иного метода: проверка исключения, нет автоматического release.

B-07. Два платежа с одинаковой суммой: сопоставление по уникальным данным, не по очереди создания заказов.

B-08. Поздняя оплата после expiry/cancel: зафиксирована и удержана от ошибочного нового исполнения; открыт план обработки.

B-09. UAH поступил, Walt недоступен: обязательство сохранено, клиент видит актуальный статус; новая USDT-команда не дублируется после восстановления.

B-10. Release завершился у провайдера, ответ потерян: status lookup восстанавливает успех без повторного release.

## 6 Клиент продаёт USDT

S-01. Штатный путь: подтверждены USDT, ровно одна UAH-выплата, дальнейшая фиксация по официальному процессу, закрытые проводки.

S-02. USDT не подтверждён: платёж UAH не создаётся.

S-03. Недостаточно свободных UAH при действующих резервах: новая сделка не принимается.

S-04. Подмена получателя после подтверждения условий: команда отклоняется; ранее подготовленная подпись/команда не используется с новым payload.

S-05. Выплата подготовлена, но не подписана в Ощад: не считается отправленной или проведённой; отображается задача подтверждения.

S-06. Банк принял документ, но ещё не провёл: нет фиктивного статуса COMPLETED.

S-07. Банк провёл платёж, ответ потерян: сначала история/выписка; второй документ не создаётся.

S-08. Банк отклонил выплату: политика определяет разрешённое повторение либо возврат USDT; учёт отражает фактический отказ.

S-09. USDT заблокированы, а банк недоступен: сохраняются резерв и обязательство, не выдаётся сообщение об успешном обмене.

S-10. Комиссия банка отличается от ожидаемой: не скрывается; превышение разрешённого лимита останавливает отправку.

## 7 Веб форма Ощад

W-01. Проверен фактический тип кабинета, домен и доступные действия; CorpLight не назначен по предположению.

W-02. Истечение сессии до отправки не вызывает расход; восстановление не создаёт новый заказ.

W-03. Истечение после возможной отправки переводит в UNKNOWN_RESULT и блокирует повтор до сверки.

W-04. CAPTCHA/OTP/подтверждение приложения/КЭП создаёт необходимую задачу, а не обходится.

W-05. Изменение структуры формы блокирует исполнение; получатель не попадает в поле суммы или назначения.

W-06. Двойной клик, refresh, back и второй worker не создают второй платёж.

W-07. Веб-статусы сохранено/подписано/отправлено/обрабатывается/проведено/отклонено отображаются раздельно по фактически доступному продукту.

W-08. Скриншот и изменение общего баланса не подтверждают конкретное входящее движение.

W-09. Автоматический режим не включается, пока нет разрешённого процесса без обязательного участия человека; наличие формы само по себе не закрывает этот пункт.

W-10. Push дедуплицирован и запускает проверку, но сам по себе не выдаёт USDT.

W-11. Баланс меняется из-за нескольких движений/удержаний: нет ошибочного присвоения одного изменения конкретному клиенту.

W-12. Push отсутствует или запаздывает: polling/история восстанавливает наблюдение; нет потери денежных обязательств.

W-13. Доступен только push и общий баланс без необходимых признаков стороны: результат предварительный, авто-release не принимается как проверенный.

W-14. Скрин оплаты повторно использован, изменён или не соответствует независимым банковским данным: USDT не выдаётся автоматически.

W-15. Вложение недоступно в собственной веб-сессии Walt: проверка скрина отмечена как assisted/unavailable; произвольные ссылки клиента не используются для загрузки.

## 8 События, повторы и сверка

R-01. Один webhook доставлен 10 раз: одно событие перехода и одна денежная операция.

R-02. События пришли в обратном порядке: более старое не откатывает завершение; конфликт не игнорируется.

R-03. Crash между созданием outbox и отправкой: worker продолжает корректно.

R-04. Crash после внешнего эффекта до записи ответа: только сверка/идемпотентное восстановление, нет слепого повтора.

R-05. Stale lease не позволяет автоматически стартовать второй browser worker: прежний процесс доказанно остановлен, владение профилем передано и внешнее состояние сверено. Fencing token БД сам не останавливает клик.

R-06. Неизвестный внешний статус: REVIEW_REQUIRED; нет автоматического оптимистичного завершения.

R-07. Платёж одного заказа пытаются использовать во втором: уникальность блокирует повторное зачисление.

R-08. Учётная проводка доставлена повторно: businessEventId предотвращает повтор.

R-09. Возврат превышает подтверждённый невозвращённый остаток: отказ. Неизвестный результат возврата: сверка до повторения.

R-10. Восстановлена старая БД при более новых внешних переводах: сначала reconciliation, опасный replay заблокирован.

R-11. Сверка выявила внешнее движение без заказа: нераспределённое движение и задача, не автоматическая прибыль.

R-12. Аварийный stop: новые расходные команды остановлены, чтение статусов и обработка уже открытых обязательств продолжаются.

## 9 Промо и воронка

P-01. COMPLETED с согласием и собственным каналом: одно приглашение с корректной ссылкой.

P-02. Дубликат completed: нет второй запланированной доставки.

P-03. Нет согласия: SKIPPED/NO_CONSENT; финансовый чек доступен.

P-04. Нет связи с собственным ботом: SKIPPED/NO_OWN_CHANNEL; сообщение в Walt не отправлено.

P-05. Клиент отменил согласие между enqueue и send: отправка не выполняется.

P-06. Отменённый, спорный, ожидающий и частично исполненный обмен не генерирует успешную рекламу.

P-07. Промо завершилось до отправки: сообщение отменено либо выбрана другая допустимая кампания с новым актуальным содержанием до отправки; старый приз не рекламируется как доступный.

P-08. Клиент уже участвует: нет обещания лишнего билета; переход ведёт на корректную страницу.

P-09. Бот заблокирован: нет бесконечного retry. Неизвестный итог send: UNKNOWN_DELIVERY, не слепой дубль.

P-10. Неисправность рекламы не блокирует завершение денег.

P-11. Переход/QR не выдаёт билет; участие учитывается только по серверному подтверждению Raffle.

P-12. Один пользователь с несколькими обменами не считается несколькими новыми привлечёнными клиентами.

P-13. В ссылке и общедоступной аналитике нет суммы обмена, банковских данных и Telegram ID.

P-14. Ссылка не позволяет произвольный redirect и не открывает чужую историю.

P-15. Режим «после каждой сделки» и добровольный суточный лимит имеют различимые результаты по каждой сделке.

## 10 Интерфейс, доступ и нагрузка

U-01. Все обязательные экраны и состояния проверены на en, uk, ru, pl, de, fr, es, it, pt, tr. Перевод названия валют не меняет актив.

U-02. Основная последовательность доступна на 320–1440 px, с клавиатурой, экранным увеличением и в Telegram safe area. Длинная сумма или ID не выталкивает кнопку подтверждения.

U-03. История доступна только владельцу; смена id и cursor не даёт чужие сделки.

U-04. Маркетолог не видит платёжные реквизиты и не выполняет release/payout.

U-05. Ключи, cookies сессии банка, OTP и КЭП не попадают в frontend, error tracking и промо payload.

U-06. При параллельной нагрузке до согласованного лимита не нарушаются резервы и idempotency. Измеряются API p95, backlog и доля исключений; лимит нагрузки фиксируется в отчёте, не выдумывается как подтверждённая производительность.

## 11 Порядок реальной проверки

Без реальных расходов сначала выполняются доменные тесты, проверка денежных инвариантов, контрактные тесты адаптеров, replay событий и чтение разрешённых аккаунтов. Это не отдельный блокчейн Testnet и не нарушение выбранного Mainnet-only направления проекта.

Перед реальными контрольными сделками фиксируются счета, получатели, объёмы по USDT/UAH, максимальные комиссии и совокупный допустимый убыток. ТЗ само по себе не является разрешением на торговлю или дебетование счетов.

Минимальный live-пакет: одна покупка клиента и одна продажа клиента с проверкой обеих сторон и остатков; проверка повторного чтения/обработки тех же событий без повторного расхода; одна допустимая доставка приглашения и подтверждённое добровольное участие в промо. Ошибочные ситуации в банке не нужно искусственно вызывать реальными потерями — их проверяют моделями и контролируемыми отказами до внешнего эффекта.

Результат каждого направления принимается отдельно. Если штатные операции требуют ручной подписи, допустимо принять assisted-режим, но строка «полный автомат» остаётся не выполненной.

## 12 Итог аудита документов

Проверка выполнена 28 октября 2026 на уровне требований, ссылок и взаимной согласованности. Исполняющий код не создавался, провайдерские полномочия и реальные деньги не проверялись.

Выявленные противоречия и исправления:

1. «USD» против изображения USDT и уточнения заказчика: область сужена до USDT ↔ UAH; банковский USD исключён.
2. По решению заказчика торговое исполнение заменено браузерным worker Walt. Market data API отделён; отдельный trading API не является зависимостью; фиктивные endpoints отсутствуют.
3. Реклама в сообщении сделки против ограничений Walt: используется собственный согласованный канал, запрещённый канал исключён явно.
4. «Сообщение после каждой сделки» против отсутствия собственного контакта: событие создаётся на каждую завершённую сделку, но доставка имеет проверяемое право и причину пропуска.
5. Автоматический fiat API против уточнения об Ощад: текущее подключение WEB_ASSISTED/WEB_AUTOMATED_VERIFIED с отдельным статусом допустимости; отдельное ТЗ на форму, без приписывания банку API.
6. «Оплачено» против фактического зачисления: заявление клиента не выпускает USDT.
7. Timeout против автоматического retry: UNKNOWN_RESULT и сверка до повторного денежного эффекта.
8. Оборот против прибыли: раздельный количественный учёт и экономический результат после расходов.
9. Обмен против участия в розыгрыше: нет автоматической покупки билета или выдачи участия; промо независимо от расчёта.
10. Подготовка веб-платежа против проведения банком: отдельные стадии и доказательство конечного результата.
11. Mainnet-only против необходимости тестов: локальные модели/replay и read-only проверки сохранены, обязательного Testnet нет.
12. Push/баланс против подтверждения оплаты: отдельный предварительный статус и правила достаточности доказательств; общее изменение баланса не присваивается клиенту автоматически.
13. Скрин клиента против независимого банковского доказательства: отдельная модель вложений, контроль повторов и запрет принятия скрина как единственного основания выдачи.
14. Изоляция модулей: торговые деньги и ключи не смешиваются с существующими розыгрышами, VRF и призовыми резервами.

Документы готовы для оценки объёма разработки и обследования фактических кабинетов. Полный автомат требует фактической проверки веб-процессов Walt и Ощад; наличие отдельных торговых API не требуется. Поддержка браузерной автоматизации Walt не подтверждена; риск ограничений аккаунта и остановки на защитах сохранён.


## 13 Сквозные сценарии после повторного аудита v1.2

Сценарии ниже проверяют [контракт 08](08-execution-contract.md). Они добавлены к C/Q/B/S/W/R/P/U и BW-сценариям, не означают их фактическое исполнение.

X-01. EC-001: native-заявка из Walt исполняется без quoteId, сайта Raffle и TON-кошелька клиента.

X-02. EC-002: повторный импорт, новое подключение и перезапуск сессии дают один orderId; исторический заказ не вызывает расход и рекламу.

X-03. EC-003: цена объявления изменилась, но текущая сделка сохраняет свой внешний снимок условий.

X-04. EC-004: counterpartyRef Walt не используется как Telegram chatId; nullable customerId не ломает импорт и учёт.

X-05. EC-005: заявка собственного UI не связалась с внешней или условия разошлись — нет инструкции платить и нет молчаливого исполнения по иной цене.

X-06. EC-006: клиент покупает USDT — без подтверждения UAH release недоступен; при обеих подтверждённых сторонах закрытие корректно.

X-07. EC-007: UAH выплачены, но контрагент ещё не передал USDT — COMPLETED/промо не создаются, обязательство сохранено.

X-08. EC-008: ESCROW_CONFIRMED не отображается как RECEIVED_CONFIRMED; fiatPhase/cryptoPhase различаются по направлению.

X-09. EC-009: недостаточно времени до deadline — новый расход не начинается; уже оплаченный заказ не отменяется по таймеру.

X-10. EC-010: истечение TTL котировки/сессии не освобождает резерв принятого/неопределённого заказа.

X-11. EC-011: один внешний escrow не считается вторым активом и не вычитается повторно из свободной ликвидности.

X-12. EC-012: недоступная история не доказывает отсутствие оплаты; поздний платёж после закрытия создаёт обязательство без второго завершения.

X-13. EC-013: после первой исполненной стороны отмена/возврат проверяет обе стороны; частичный возврат не обозначается полным.

X-14. EC-014: lease истёк, старый executor всё ещё может кликнуть — второй не запускается. После доказанной остановки — только сверка, затем разрешённое восстановление.

X-15. EC-015: человек взял профиль вручную — авто-клики остановлены; после передачи обратно выполнена сверка.

X-16. EC-016: смена sequence/worker/UI version не создаёт второй RELEASE_USDT или PAY_UAH по одной обязанности.

X-17. EC-017: crash после ATTEMPT_STARTED, но до ответа — UNKNOWN_RESULT, не повторный клик по отсутствующему локальному результату.

X-18. EC-018: после выполненной выплаты аварийный stop блокирует новые расходы, но допускает безопасную отметку оплаты по доказанному документу при распознанном UI.

X-19. EC-019: свои BUY/SELL объявления созданы/изменены/поставлены на паузу и результат проверен в Walt; финансовая публикация не включается одним market data ключом.

X-20. EC-020: активные заказы и комиссия уменьшают доступный объём объявления; изменение объявления не переоценивает уже принятые сделки.

X-21. EC-021: команда pause потеряла ответ — AD_PAUSE_UNCONFIRMED, а не ложное «объявление выключено».

X-22. EC-022: собственное объявление не входит в конкурентный референс; зацикленное понижение/повышение курса и дубликат объявления после edit timeout исключены.

X-23. EC-023: несколько заказов внешнего Auto-Accept сверх локального лимита всё равно импортированы, учтены и приоритизированы по deadline.

X-24. EC-024: скрин, push и баланс сохраняют разные уровни доказательств; нельзя повысить уровень без данных/проверяющего.

X-25. EC-025: доступны только общий баланс и недостаточно подробный push — шаг остаётся assisted, полная автоматизация не отмечается пройденной.

X-26. EC-026: поддельный/replayed/старый push и потеря heartbeat устройства не подтверждают новый платёж.

X-27. EC-027: знание номера сделки, имени и скрина не связывает чужой заказ с нашим ботом и не раскрывает его историю.

X-28. EC-028: для native-клиента без доказанной связи записан NO_VERIFIED_CUSTOMER_LINK; в Walt реклама не отправлена.

X-29. EC-029: новое прочтение COMPLETED, возврат или редактирование шаблона не создают новый completionEventId/вторую доставку.

X-30. EC-030: схема допускает native-заказы без quote/customer, соблюдает уникальность внешнего заказа и хранит владение сессией.

X-31. EC-031: один банковский документ с комиссией и разными movementType не может оплатить две сделки сверх фактического principal.

X-32. EC-032: приёмка каждого направления требует обеих сторон, сверки и проверенного восстановления; расход вне согласованных лимитов не выполняется.

## 14 Дополнительные сквозные сценарии v1.3

X-33. EC-033: заказ завершился во время сбоя и впервые увиден terminal после перезапуска — не потерян как historical, сверён без расхода, создано максимум одно новое завершение; baseline не пересоздан.

X-34. EC-034: до принятия реквизиты скрыты — приём допустим по своей policy, выплата запрещена; после раскрытия фиксируется paymentDetailsHash; смена зафиксированного получателя блокирует расход.

X-35. EC-035: банк провёл UAH, но загрузка квитанции в Walt потеряла ответ — проверяются вложения того же заказа, повторной выплаты нет; чужая квитанция не прикрепляется.

X-36. EC-036: сотрудник подтвердил только скрин/общий баланс без достаточных данных — MANUAL_VERIFIED и release недоступны; документированное достаточное банковское подтверждение допускает assisted-шаг.

X-37. EC-037: поздний push, одинаковый текст двух реальных платежей, переустановка сборщика и seq reset не теряют обязательства и не подтверждают новый заказ по старому событию.

X-38. EC-038: два объявления одновременно используют один остаток — общий бюджет не превышен; недоступный контроль внешнего Auto-Accept не заменён локальным флагом приёма.

X-39. EC-039: комиссия в USDT и комиссия в UAH рассчитаны по своей стороне/базе; gross/net не смешиваются; резерв покрывает merchantDebit, неизвестная комиссия не равна нулю.

X-40. EC-040: снимок available уже учитывает escrow — нет повторного вычитания; неизвестная принадлежность lock к снимку останавливает новый приём; восстановленный baseline не удваивает активы.

X-41. EC-041: часы устройства отстают, UI показывает относительный таймер или observedAt устарел — новый расход не начинается по ошибочному deadline; проведённый платёж не объявляется отменённым.

X-42. EC-042: спор/отмена/смена реквизитов произошли после подготовки действия — новое чтение блокирует клик; если эффект уже произошёл, отражается фактически и не компенсируется вторым непроверенным расходом.

X-43. EC-043: отсутствует лимит, комиссия или допустимый счёт — read-only доступен, финансовое исполнение/публикация не включаются; отсутствие настройки не даёт unlimited.

X-44. EC-044: отзыв согласия до dispatch отменяет отправку; отзыв после начала внешнего запроса не выдаётся за гарантированное удаление; UNKNOWN_DELIVERY не разрешает слепой повтор.
