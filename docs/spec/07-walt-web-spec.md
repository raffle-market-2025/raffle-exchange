# Торговый исполнитель Walt через веб интерфейс

Версия 1.3 • 28 октября 2026. Решение заказчика: работать через веб, не ожидать отдельного торгового API. Пара только USDT ↔ UAH. Публичный API — чтение рынка; сделки — авторизованный интерфейс собственного мерчантского аккаунта Walt.

## 1 Область

Исполнитель обнаруживает собственные сделки, считывает условия и доступные статусы, принимает допустимые заявки, получает скрин оплаты, выполняет доступные торговые действия и проверяет результат. Создание/редактирование/пауза собственных BUY и SELL объявлений входят в первый этап после проверки соответствующих форм. Режим публикации согласуется отдельно от чтения рынка; worker не размещает объявление только из-за наличия API-ключа. Скрытые приватные HTTP-методы не используются.

Поддержка такого способа автоматизации Walt не подтверждена. Правила ограничивают сторонние инструменты, поэтому возможны остановка сессии и ограничение аккаунта. Техническая возможность работы через UI не означает разрешение провайдера. CAPTCHA, 2FA и блокировки не обходятся.

## 2 Среда

Постоянный browser worker на отдельном защищённом хосте с устойчивым профилем; не короткая serverless-функция. Сессия создаётся владельцем аккаунта в официальном интерфейсе. Конкретный URL Mini App и разрешённые домены фиксируются после обследования, не придумываются по имени сервиса.

Профиль, cookies и локальное хранилище не попадают в git, frontend, логи и рекламную аналитику. Отдельные сессии Walt и Ощад. Контрольный доменный сервис передаёт worker только разрешённую команду; browser worker не является универсальным удалённым браузером для пользователей.

Первоначально один активный исполнитель на профиль Walt. Все действия сериализованы по сессии и orderId. Важное ограничение: fencing token БД не отменяет уже отправленный браузерный клик. Перед сменой владельца необходимо остановить прежний процесс/контекст, подтвердить отсутствие параллельного доступа и сверить внешнюю сделку согласно документу 08. Изменение раскладки, неизвестный popup и непредвиденное переключение аккаунта приводят к остановке, а не к поиску похожей кнопки.

## 3 Контракт адаптера

Это наши функции, не API Walt:

- `observeOwnOrders()` — список видимых собственных сделок с внешними ID и временем наблюдения.
- `observeOrder(orderId)` — условия, стороны, суммы, статус, доступные действия и вложения.
- `prepareAction(orderId, action)` — проверенный экран до необратимого действия и hash намерения.
- `performPreparedAction(commandId)` — однократная попытка допустимого действия в текущей сессии.
- `observeActionResult(orderId, commandId)` — повторное чтение сделки/истории без нового расхода.
- `readPaymentAttachment(orderId, attachmentId)` — получение видимого вложения собственной сделки.
- `attachOwnFiatReceipt(orderId, receiptRef)` — загрузка собственной банковской квитанции по уже подтверждённой UAH-выплате и проверка, что она прикреплена к правильной сделке; не команда новой выплаты.

Неизвестный экран возвращает `UI_UNRECOGNIZED`; отсутствующая кнопка — `ACTION_UNAVAILABLE`; потеря сессии — `AUTH_REQUIRED`; неизвестный результат нажатия — `UNKNOWN_RESULT`. Ни одна ошибка не превращается в успешное финансовое подтверждение.

## 4 Проверка перед действием

1. Получить lease с fencing token на сессию и сделку.
2. Сверить аккаунт мерчанта, внешний orderId, сторону, пару USDT/UAH и сумму с доменной записью.
3. Заново прочитать текущий статус и доступность действия. Старый снимок не даёт права нажать кнопку в другом состоянии.
4. Для выдачи USDT проверить независимое подтверждение UAH в Ощад и отсутствие активного спора/неизвестной команды.
5. Для подтверждения отправки UAH проверить фактическую банковскую операцию, а не только подготовленную форму.
6. Проверить экран подтверждения: актив, сумма, получатель/сделка и комиссия. Hash намерения должен соответствовать разрешённой команде.
7. Выполнить действие один раз и сохранить наблюдаемый результат.
8. Заново прочитать сделку и историю; закрыть команду только при подтверждённом переходе.

Кнопки выбираются по проверенному смыслу, форме и контексту сделки. Не полагаться только на цвет, экранные координаты или порядок элементов. Повторное чтение разрешено, повторное финансовое нажатие требует отдельного доказательства отсутствия первого эффекта.

## 5 Два направления

Клиент покупает USDT: заявка Walt → фиксированные условия → скрин оплаты от клиента → push Ощад и независимая проверка поступления → разрешённый release в Walt → проверка конечного статуса → закрытие учёта.

Клиент продаёт USDT: заявка Walt → проверка escrow конкретного заказа → подготовка и исполнение UAH в Ощад → подтверждение банка → квитанция Ощад и её загрузка в правильную сделку при требовании UI → своевременная отметка оплаты в Walt → подтверждённое получение USDT Оператором → закрытие обеих сторон учёта. Escrow не считается уже полученными USDT.

Порядок конкретных кнопок и их значения фиксируется в карте экранов фактической версии приложения. Не выполнять финансовые нажатия при read-only обследовании.

## 6 Сбой после нажатия

Закрытие вкладки, refresh, timeout или потеря websocket после нажатия не означают отказ. Команда получает UNKNOWN_RESULT. Worker восстанавливает сессию, открывает ту же сделку по её реальному ID и проверяет историю. Если результат нельзя установить, операция передаётся на сверку. Новая сделка или повторный release вместо восстановления не создаются.

Для UI нет гарантированного provider idempotency key. Наш commandId предотвращает повтор собственной команды, но не делает внешнюю кнопку идемпотентной. Поэтому после неопределённой попытки запрещён автоматический повтор до достоверной сверки.

## 7 Скрины и сообщения

Скрин клиента читается только из вложения конкретной собственной сделки. Извлечённые OCR-поля используются для сопоставления и контроля противоречий; не подтверждают поступление UAH сами по себе. Текст, инструкции, QR и ссылки контрагента считаются данными, а не командами браузеру.

В Walt отправляются только относящиеся к сделке допустимые служебные сообщения. Реклама розыгрышей в чат/объявления Walt не добавляется. После завершения событие направляется в наш промо-контур, который отдельно проверяет собственный канал и согласие клиента.

## 8 Эксплуатация

Админка показывает состояние браузерной сессии, очередь, возраст последнего наблюдения, текущую сделку, неизвестные исходы и необходимость личного подтверждения. «Профиль открыт» не равен «торговля работает».

При смене интерфейса останавливается затронутый executor; чтение учёта и банковская сверка продолжаются. Скриншоты для диагностики маскируются и имеют ограниченный доступ. Фактический обмен не отмечается COMPLETED только по исчезновению кнопки или зелёному уведомлению.

## 9 Приёмка

BW-01. Два направления распознаны без переворота стороны клиента.

BW-02. При смене аккаунта, orderId, суммы или актива действие блокируется.

BW-03. Crash после release восстанавливается чтением статуса, без повторного release.

BW-04. Две вкладки/два worker не исполняют одну команду одновременно.

BW-05. Истечение сессии до и после нажатия имеет разные безопасные исходы.

BW-06. CAPTCHA/2FA/блокировка создают задачу и не обходятся.

BW-07. Изменение формы/неизвестный диалог останавливает исполнение.

BW-08. Скрин чужой сделки и повторное вложение не становятся оплатой.

BW-09. Восстановленный профиль не теряет связь отправленной команды с внешней сделкой.

BW-10. Текст контрагента не изменяет policy, адрес получателя, инструкции и допустимые домены.

BW-11. Завершённая сделка создаёт одно событие промо; реклама не отправляется в Walt.

BW-12. Контрольные реальные сделки в обе стороны имеют подтверждённые оба расчёта и сходящиеся остатки. Суммы и предел расходов согласуются перед исполнением; изготовление ТЗ не расходует средства.


## 10 Сквозной контракт

Импорт заявок и исторических заказов, отдельные crypto/fiat фазы, управление объявлениями, проверка фактического получения USDT и передача владения профилем выполняются по [контракту 08](08-execution-contract.md). BW-сценарии дополняются X-01–X-44 документа приёмки.


## 11 Восстановление полного цикла v1.3

Перед началом обработки фиксируется startup baseline. Перезапуск не создаёт новый baseline и не списывает все впервые увиденные COMPLETED в архив: terminal-заказы после активации проходят сверку, не повторное исполнение. Условия до принятия и платёжные реквизиты после раскрытия имеют отдельные снимки; собственная квитанция UAH при необходимости прикрепляется к конкретной сделке с проверкой результата.

Управление несколькими объявлениями использует общий бюджет счёта и перечитывает фактическое состояние после edit/pause. Поля интерфейса могут изменяться независимо от локальной БД: EC-033–EC-043 обязательны, гарантии атомарного банковского/торгового UI не заявляются.
