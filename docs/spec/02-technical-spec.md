# Техническое ТЗ на автоматический обмен USDT и UAH

Версия 1.3 • 28 октября 2026. Область: только USDT ↔ UAH. Требования основного ТЗ обязательны вместе с этим документом. Все перечисленные ниже торговые интерфейсы — внутренние контракты нашего сервиса, а не заявление о наличии таких методов у публичного API Walt.

Текущее банковское подключение — Ощад через веб-форму, без предполагаемого API. Для него обязательны [уточняющие требования](06-oschad-web-spec.md). Абстрактные банковские возможности ниже означают функции адаптера и не утверждают существование HTTP-методов банка.

## 1 Границы компонентов

### 1.1 Клиентское приложение

Отвечает за форму, показ условий, подтверждение, историю и блок промо. Не получает ключ Walt, банковские секреты, полномочия расходования или полный ответ служебного адаптера. Доверять суммам, курсу, времени истечения и статусу от браузера нельзя.

### 1.2 Exchange API

Аутентификация, валидация, котировки, приём команд, чтение состояния, доступ к истории. Обращение к API не ожидает всего расчётного цикла; длительная операция возвращает идентификатор и актуальное состояние. Endpoint не держит банковскую транзакцию открытой во время внешнего HTTP-запроса.

### 1.3 Market data adapter

Получение объявлений Walt через официально подтверждённый host; нормализация рыночной стороны; фильтрация USDT/UAH и разрешённых методов; отметка времени источника и времени получения. Используется для референса, не для фиктивного подтверждения сделки.

### 1.4 Trade execution adapter

Браузерный исполнитель работает с видимыми формами собственной сессии Walt: чтение своей очереди, открытие сделки, проверка её параметров, получение вложения, доступные действия принятия/отмены/release и проверка результата. Каждое действие разрешается только после обследования соответствующего экрана. Отдельные trading endpoints не предполагаются. При CAPTCHA, повторной авторизации или неизвестной форме — остановка и задача сотруднику. Подробности в [ТЗ веб-исполнителя](07-walt-web-spec.md).

### 1.5 Fiat adapter

Отдельные полномочия чтения банковских поступлений, чтения исходящих платежей и создания разрешённой выплаты UAH. Если конкретный банковский продукт позволяет только выписку, выплата через него не считается доступной. Доступ к персональному кабинету не равен праву серверного исполнения.

### 1.6 Исполнение и учёт

Order engine хранит состояния, policy engine проверяет разрешение на каждую команду, ledger хранит двойные проводки, reservation service управляет ликвидностью. Durable worker выполняет внешние операции через outbox. Reconciler независимо сверяет фактические состояния и обязательства.

### 1.7 Промо интеграция

Получает только событие подтверждённого завершения и минимальные данные для разрешённой доставки. Не может подтверждать платёж, завершать сделку или менять размер обмена.

## 2 Реестр возможностей

Для каждого подключения хранить версионированный список:

- `read_market_ads`;
- `read_own_orders`;
- `create_order`;
- `manage_own_ads`;
- `accept_order`;
- `mark_fiat_sent`;
- `release_crypto`;
- `cancel_order`;
- `read_escrow`;
- `read_crypto_settlement`;
- `read_fiat_incoming`;
- `create_fiat_payout`;
- `read_fiat_payout`;
- `transactional_webhook`;
- `idempotent_command`;
- `lookup_command_by_reference`;
- `own_bot_promo_delivery`.

Каждая возможность имеет `supported`, `verifiedAt`, `evidenceRef`, `providerVersion`, `scope` и проверенный набор ограничений. Непроверенная возможность трактуется как недоступная. Для веб-действий evidenceRef ссылается на проверенный экран и результат контрольного сценария. Полномочия сессии и позиция провайдера по автоматизации учитываются отдельно; техническая доступность кнопки не доказывает поддержку автоматизации.

Автоматическая покупка клиента требует проверенного действия Walt по выдаче USDT и надёжного подтверждения UAH. Автоматическая продажа клиента требует подтверждения USDT и проверенного процесса выплаты UAH. Для браузерного исполнения внешний orderId и история сделки служат основанием восстановления. Если после нажатия нельзя достоверно установить исход, повтор расходного действия блокируется до сверки.

## 3 Подключение рыночных данных Walt

Документированный метод: `POST /p2p/integration-api/v1/item/online`; авторизация — `X-API-Key`; параметры: `cryptoCurrency`, `fiatCurrency`, `side`, `page`, `pageSize`. Запрашивать только `USDT`, `UAH`, стороны `BUY` и `SELL`. Максимальная документированная страница — 50 объявлений. [Документация Walt](https://docs.walt.io/p2p).

Домены в документации и справочном примере отличаются (`p2p.walletbot.me` и `p2p.walt.io`). Использовать один подтверждённый провайдером адрес в конфигурации. Не пробовать ключ последовательно на разных доменах и не следовать перенаправлению с передачей секрета.

Сторона BUY/SELL в рыночном ответе относится к объявлению. Привязку к нашим понятиям «клиент покупает» и «клиент продаёт» проверить на контрольных объявлениях; сохранить отдельную функцию отображения и тест. Никогда не делать вывод по цвету кнопки приложения.

При ошибках 401/403 останавливать обновления этого подключения и уведомлять о доступе; 429 — учитывать Retry-After и ограничивать запросы; 5xx — backoff с jitter. HTTP 200 требует проверки бизнес-статуса и схемы данных. Неизвестная валюта, нечисловая цена, отрицательный остаток и нарушенные min/max не попадают в расчёт.

Проектный интервал чтения — не чаще полезной частоты обновления источника, с общим лимитером на ключ. Начальный polling 30 секунд и порог stale 90 секунд — параметры проекта, а не обещание провайдера. Хранить `fetchedAt`, `sourceAt` если доступно и `staleReason`. Если sourceAt отсутствует, не выдавать fetchedAt за время обновления рынка.

Нельзя получать гарантированный курс на суммарный объём, просто сложив страницы объявлений: объявления не являются нашим резервом исполнения.

## 4 Внутренние модели и единицы

### 4.1 Котировка

Поля `quoteId`, `customerId`, `direction`, `inputAsset`, `inputAmount`, `outputAsset`, `outputAmountNet`, `priceUahPerUsdt`, `fees[]`, `paymentMethodId`, `settlementRouteId`, `inventoryReservationId`, `createdAt`, `expiresAt`, `tariffVersion`, `policyVersion`, `sourceSnapshotId`, `termsHash`.

`direction` принимает только `CUSTOMER_BUYS_USDT` или `CUSTOMER_SELLS_USDT`. Asset принимает только `USDT` или `UAH`; для каждого направления сервер проверяет порядок пары. Внешний блокчейн, если поддержан официальным маршрутом, хранится отдельно от asset; перевод на другой network не превращается в другую валюту.

### 4.2 Сделка

Обязательные инварианты этого процесса определены в [контракте 08](08-execution-contract.md); его требования к escrow, резервам и владению браузером применяются ко всем адаптерам.

Поддерживаются `origin=WALT_NATIVE` (первый этап) и `origin=OWN_UI` (дополнительный). У native-сделки `customerId` и `quoteId` могут отсутствовать: идентичность контрагента хранится как отдельная область Walt, а условия берутся из конкретного внешнего заказа. Это не даёт права считать его пользователем нашего бота. Модель связывания и импорт описаны в [контракте 08](08-execution-contract.md).

Поля `orderId`, `origin`, `customerId` (nullable для native), `counterpartyRef`, `quoteId` (nullable для native), `direction`, `merchantAccountId`, `providerOrderId`, `providerOrderVersion`, `paymentMethodId`, `receivingAccountRef`, `state`, `exceptionReason`, `version`, `acceptedTermsHash`, `acceptedAt`, `paymentDeadline`, `createdAt`, `completedAt`.

Один непустой quote принимается максимум одной сделкой; у native-заказа внешние условия являются исходным снимком. Принятые денежные условия неизменяемы; реквизиты, скрытые до принятия заказа, фиксируются отдельно после их раскрытия и до расхода. После paymentDetailsHash получатель неизменяем. Если необходимо другое предложение — новая котировка и новое согласие до денег.

### 4.3 Подтверждение расчёта

`settlementEvidence`: источник, внешний ID операции, направление, точные суммы/валюта, статусы и версия провайдера, плательщик/получатель в доступной проверенной форме, время, подпись или идентификатор запроса проверки, хеш исходных данных, ссылка на зашифрованный артефакт.

Публичный API объявлений не является источником settlementEvidence. Квитанция клиента — вложение к спору, не основание автоматической выдачи USDT.

## 5 Состояния

Котировка: `DRAFT → OFFERED → ACCEPTED`; альтернативы `EXPIRED`, `REJECTED`, `SUPERSEDED`. `ACCEPTED` нельзя вернуть в `OFFERED`.

Сделка:

- `CREATED`: условия приняты, создан собственный ID, внешний заказ ещё не подтверждён.
- `PROVIDER_PENDING`: команда направлена, результат создания/принятия уточняется.
- `AWAITING_CUSTOMER_PAYMENT`: клиент должен передать исходный актив согласно направлению.
- `CUSTOMER_PAYMENT_REPORTED`: клиент сообщил об оплате, независимого подтверждения пока нет.
- `FIAT_SIGNAL_RECEIVED`: получен банковский push или обнаружено изменение баланса; требуется проверка конкретного движения и однозначности.
- `INBOUND_VERIFIED`: подтверждена необходимая оплата/escrow по правилам маршрута.
- `OUTBOUND_PREPARED`: выплата или release подготовлены, policy и резерв проверены.
- `OUTBOUND_SUBMITTED`: команда ушла; неизвестный итог не разрешает повторный расход.
- `OUTBOUND_CONFIRMED`: внешний канал подтвердил требуемый расчёт.
- `RECONCILING`: проверяются обе стороны, комиссии и проводки.
- `COMPLETED`: выполнены все условия закрытия; событие промо допустимо.
- `CANCELLED`: нет открытых денежных обязательств и неразрешённого исполнения.
- `EXPIRED_UNFUNDED`: срок истёк, подтверждено отсутствие оплаты и расходных команд.
- `REVIEW_REQUIRED`: неоднозначная ситуация; причина и допустимый план восстановления обязательны.
- `DISPUTED`: открыт спор, автоматическое расходование остановлено по policy.
- `REFUND_PENDING`, `REFUND_SUBMITTED`, `REFUNDED`: отдельная последовательность возврата подтверждённых средств.

Это внутренние состояния, не имена состояний Walt. Адаптер имеет документированное отображение каждого внешнего статуса. Неизвестный внешний статус приводит к REVIEW_REQUIRED. Для маршрута, где Walt требует несколько зависимых действий, дополнительно хранятся фазы crypto/fiat; линейный статус не скрывает незавершённую вторую фазу.

Каждый переход выполняется compare-and-swap по `version`, внутри транзакции БД с сохранением события и будущей команды. Повтор одного события не меняет уже выполненный переход.

### Инварианты завершения

`COMPLETED` разрешён только если:

1. Внешняя сделка известна и соответствует зафиксированному внешнему снимку native-заказа либо принятой собственной котировке.
2. Входящая сторона подтверждена разрешённым источником; MANUAL_VERIFIED также опирается на объективные банковские данные, не только решение сотрудника.
3. Исходящая сторона подтверждена, получатель и сумма совпадают.
4. Нет неизвестного исхода команды, активного спора и двойного использования одного входящего платежа.
5. Проводки записаны, комиссии распознаны, резервы погашены корректно.
6. При спорной обратимости банковской операции применена утверждённая политика риска; слово completed не обещает невозможность будущего chargeback.

После завершения возможен отдельный dispute/adjustment; история завершения не удаляется. Новая претензия не создаёт повторное приглашение.

## 6 Две последовательности исполнения

### Клиент покупает USDT

Создать/принять подтверждённый заказ в интерфейсе Walt → получить точные инструкции → ожидать UAH → сопоставить подтверждённый входящий платёж → проверить резерв USDT → выполнить разрешённый release/перевод → запросить внешний итог → закрыть проводки → создать `exchange.completed`.

### Клиент продаёт USDT

Импортировать/принять заказ Walt и зарезервировать UAH → подтвердить escrow USDT конкретного заказа → подготовить уникальную выплату UAH на зафиксированные реквизиты → отправить → проверить статус банка → отметить оплату в Walt в пределах внешнего срока → дождаться подтверждённого получения USDT Оператором → закрыть обе стороны учёта → создать `exchange.completed`. Escrow и состояние «оплачено» не заменяют фактическое получение USDT.

Недопустимо предполагать, что внутреннее зачисление Walt является прямой on-chain транзакцией. Для внутренней операции достаточно и необходимо надёжное доказательство провайдера; внешний blockchain explorer его не заменяет.

## 7 Платежи и сопоставление

Для текущего Ощад доверенный источник — разрешённая банковская история/выписка с устойчивыми идентификаторами и конечными статусами; способ получения определяется фактическим кабинетом. При недостаточных данных используется контролируемая работа оператора. Если официальный API/подписанное событие появится позднее, оно подключается отдельным адаптером с проверкой конечного статуса. SMS, push, OCR и LLM не дают автоматического подтверждения расчёта.

Входящий платёж связывается с одной сделкой по внешнему банковскому ID и набору проверяемых параметров. Совпадение только суммы недостаточно. Две оплаты одинакового размера не распределяются по принципу «первая свободная».

Недоплата и частичная оплата не вызывают пропорциональную выдачу USDT без отдельной поддержанной модели. Переплата создаёт обязательство на разницу. Несколько платежей одного заказа допускаются только если это явно разрешено каналом и условиями; иначе REVIEW_REQUIRED.

Поступление после отмены или expiry сохраняется в отдельной очереди нераспределённых средств. Если подтвердить назначение нельзя, средства не становятся доходом.

## 8 Надёжная очередь и внешний эффект

Команды имеют ключ вида `connectionId:orderId:operation:sequence`. Дополнительно сохраняются `payloadHash`, сумма, актив, получатель, внешний reference, время отправки, lease token и срок проверки результата.

Алгоритм:

1. Транзакция БД записывает событие, изменение состояния и outbox command.
2. Worker получает lease с fencing token. Для браузерного эффекта дополнительно требуется доказанное прекращение прежнего executor; lease БД не способен отозвать уже идущий клик в Walt/Ощад. Правило передачи владения в документе 08 обязательно.
3. Перед расходом проверяет глобальный stop, состояние, лимиты, резерв, hash payload и актуальность полномочий.
4. Внешняя команда получает idempotency key, если поддержан официально.
5. Ответ и внешние идентификаторы фиксируются до подтверждения обработки очереди.
6. При crash/timeout команда переходит в `UNKNOWN_RESULT`; выполняется status lookup по внешнему reference.
7. Повторная отправка допустима только если официальный контракт гарантирует её безопасность или достоверно подтверждено, что первая попытка не исполнялась.

Exactly-once не заявляется как свойство транспорта. Цель — отсутствие второго денежного эффекта за счёт устойчивого состояния, уникальных ключей и сверки. Истёкший lease не доказывает отсутствие уже отправленной выплаты. При невозможности определить исход ручное расследование предпочтительнее повторного расхода.

## 9 Учёт денег

Двойные проводки по каждому активу; дебеты и кредиты сходятся отдельно в UAH и USDT. Нельзя балансировать USDT-проводку прибавлением UAH. Для оценки результата сохраняются согласованная база оценки и версия курса, отдельно от количественного учёта.

Классы счетов: собственные средства в банке, собственные USDT у провайдера, средства в пути, обязательства клиентам, escrow/заблокированные остатки, комиссии, торговый результат, округления, возвраты и нераспределённые поступления.

Каждый journal имеет уникальный `businessEventId`; каждое внешнее движение — уникальное соответствие `provider + account + transactionId + movementType`. Комиссия может ссылаться на тот же внешний документ, но это отдельное типизированное движение, а не второе использование оплаты.

Резервы ликвидности — отдельная модель доступности, не дополнительный актив. Количественное обеспечение и бухгалтерская оценка не дублируют одно и то же состояние счёта.

Пример сверки покупки 100 USDT за 4 200 UAH без комиссии: подтверждённые собственные UAH увеличились на 4 200; USDT уменьшились на 100; клиентское обязательство погашено на согласованные суммы; экономический результат определяется стоимостью выбывших USDT и затратами, а не всей суммой 4 200 UAH.

## 10 База данных

Отдельная схема `exchange`; секреты в таблицы обычных настроек не помещать.

- `provider_connections`: тип провайдера, режим, разрешённые host, scopes, версия и состояние.
- `provider_capabilities`: подтверждения возможностей и ограничения.
- `market_snapshots`, `market_ads`: нормализованные объявления и свежесть; ограниченное хранение.
- `pricing_policies`, `fee_schedules`: версионированные формулы, шаги округления и сроки действия.
- `quotes`, `orders`: денежные строки, immutable terms, версии и текущий статус.
- `order_events`: неизменяемый журнал с причинностью и actor.
- `settlement_evidence`: ссылки на доказательства, hashes и проверенный статус.
- `payment_attachments`: скрины клиента, способ получения из собственной авторизованной сделки, hash и извлечённые OCR-поля; не источник финального подтверждения.
- `inbound_payments`, `payouts`, `refunds`: независимые движения и их привязка.
- `bank_notification_inbox`, `card_balance_observations`: дедуплицированные push и доверенные снимки баланса; не подменяют settlement_evidence.
- `liquidity_reservations`: актив, объём, владелец и жизненный цикл.
- `ledger_accounts`, `ledger_journals`, `ledger_entries`: двойная запись.
- `command_outbox`, `provider_event_inbox`: команды и дедупликация внешних событий.
- `reconciliation_runs`, `reconciliation_items`: сверка, расхождения и решения.
- `customer_links`: подтверждённые связи собственных пользователей и каналов; никакого угадывания по имени.
- `message_consents`, `promo_deliveries`, `attribution_events`: отдельный маркетинговый контур.
- `audit_log`: настройки, права и ручные действия.

Обязательные ограничения: unique принятый quote, unique внешний заказ в пределах подключения, unique банковское движение в пределах счёта, unique businessEventId, unique command key, unique completion event на order. Публичные ID непоследовательные; это не заменяет авторизацию.

Суммы `numeric` с достаточной точностью; максимальная точность и scale фиксируются адаптером и миграцией, чрезмерная дробность отклоняется. Даты timestamptz, внутри UTC; в интерфейсе пользовательская зона, для операционных отчётов Europe/Kyiv. Состояния БД не зависят от языка интерфейса.

## 11 Наш клиентский API

Все пути — проектируемые интерфейсы Raffle, дополнительные для OWN_UI. Они не являются endpoints Walt и не обязательны для первого WALT_NATIVE-этапа. Native-заказы поступают через внутренний импорт browser worker; маркетинговый пользователь/quote для них не создаются искусственно.

- `GET /api/exchange/config`: активные направления, режим, методы, ограничения и версии; без секретов и гарантированных цен.
- `POST /api/exchange/quotes`: направление, исходная сумма/актив и метод; ответ с неизменяемыми условиями и expiry. Сервер привязывает пользователя к сессии.
- `POST /api/exchange/orders`: quoteId, termsHash и idempotency key; один quote — одна сделка. Создаёт только допустимую при текущих capabilities операцию.
- `GET /api/exchange/orders/:id`: собственная сделка и допустимые действия.
- `GET /api/exchange/orders`: курсорная история только своего пользователя.
- `POST /api/exchange/orders/:id/payment-reported`: заявление клиента без смены статуса на verified.
- `POST /api/exchange/orders/:id/cancel-request`: запрос отмены с проверкой фактических обязательств.
- `POST /api/exchange/orders/:id/support`: обращение; не финансовая команда.
- `POST /api/exchange/message-preferences`: подтверждение/отзыв собственного согласия с версией текста и канала.

Значения ответа при ошибке: стабильный `code`, локализуемое сообщение, `correlationId`, `retryable` и известный статус. Нельзя рекомендовать автоматический retry пользователю, если он может создать вторую выплату. Секреты, банковские токены и внутренние raw payload не возвращать.

Для текущего веб-режима источники событий — наблюдения browser worker и разрешённый сборщик push; отсутствие вебхука не блокирует процесс. HTTP-уведомления собственного сборщика аутентифицируются и имеют защиту от replay; это не подпись банка. Будущие официальные вебхуки подключаются отдельно: отдельный маршрут по провайдеру, проверка подписи/секрета по официальной схеме, временного окна и replay. Если подпись недоступна, событие рассматривается как сигнал к авторизованному чтению статуса, а не доверенное подтверждение. Подтверждать приём только после устойчивой записи inbox; обрабатывать вне запроса.

## 12 Сверка и восстановление

Оперативная сверка незавершённых заказов, периодическая сверка остатков и итоговая суточная сверка по каждому счёту. Частоты зависят от rate limits; проектная цель — обнаружить неизвестный исход обычной операции в течение 5 минут, при доступном провайдере.

Контролируются: открытые внешние заказы без внутреннего соответствия, внутренние без внешних, движения без заказа, несходящиеся комиссии, зависшие резервы и расхождения остатков. Каждый пункт имеет сумму, возраст, степень риска и допустимый план.

После рестарта worker поднимает незавершённые команды и заново просматривает изменившиеся внешние заказы с перекрытием проверяемого периода; не начинает с новой чистой очереди. Terminal-заказ, впервые увиденный после сбоя, не объявляется историческим автоматически. Стартовый baseline хранится отдельно, курсор обновляется только после устойчивого импорта всей порции. Восстановление из БД не теряет историю отправленных внешних команд. Если резервная копия старее внешнего исполнения, сначала сверка внешних операций; немедленный replay старого outbox запрещён.

Изменение администратором статуса не должно скрывать расхождение. Закрытие расхождения требует ссылки на фактическую операцию либо подписанного решения с корректирующими проводками.

## 13 Секреты и политика исполнения

Текущие секреты: рыночный API-ключ и отдельные браузерные сессии Walt/Ощад; торговые/банковские API-ключи не предполагаются. Если интерфейс не разделяет права чтения и расхода, это отражается как широкие полномочия сессии и компенсируется ограничениями worker и доменной policy, а не фиктивными scopes. Секреты только на сервере, в разрешённом защищённом хранилище; маскирование логов и ротация обязательны.

Policy проверяет актив USDT/UAH, конкретное подключение, счёт/получателя, разрешённый тип операции, per-order/day лимиты и реальный доступный остаток. Изменение получателя или суммы инвалидирует подготовленную команду. Нет универсального API «отправить на произвольный адрес» в клиентском или рекламном контуре.

Персональные данные минимизируются и шифруются; UI показывает маску, полный просмотр доступен ограниченной роли и журналируется. Сроки хранения определяются утверждённой политикой для реального Оператора и его расчётных каналов. Заявка на удаление данных не стирает обязательный финансовый журнал; маркетинговые связи можно отозвать независимо.

## 14 Логи, тревоги и целевые показатели

Логи: correlationId, orderId, переход состояния, команда, latency, код провайдера, retry count. Запрещены ключи, полный PAN, документы клиента и содержимое приватных сообщений.

Тревоги: недоступность провайдера, неизвестный результат расхода, приближение к deadline, недостаток ликвидности, несходящийся баланс, replay/подмена webhook, backlog очереди, выросшая доля отказов и сбои доставки промо.

Начальные проектные цели: чтение нашей истории p95 до 1 секунды при согласованной нагрузке; расчёт котировки из свежего локального snapshot p95 до 2 секунд; решение о промо до 10 секунд после completed; допустимая задержка внешнего расчёта показывается по фактическому провайдеру. Эти цели проверяются нагрузочным тестом, не выдаются за SLA Walt.

Технические метрики маркируются направлением и подключением, но не банковскими реквизитами или полным Telegram ID. Широковещательная аналитика лендинга не используется как источник финансового учёта.

## 15 Предлагаемая структура реализации

`apps/exchange-web` — клиентский UI; `services/exchange-api` — свои маршруты и авторизация; `services/exchange-worker` — исполнение и сверка; `packages/exchange-domain` — деньги, состояния и инварианты; `packages/walt-adapter` — рыночный API и доменный контракт; `services/walt-browser-worker` — торговый веб-исполнитель; `packages/fiat-adapter` — банк; `packages/exchange-ledger` — учёт; `packages/promo-acquisition` — события и доставка; `tests/contracts`, `tests/scenarios`, `docs`.

Это проектная структура будущего кода, а не созданные приложения. Можно вынести в отдельный приватный репозиторий при реализации, сохранив взаимодействие с Raffle через узкие серверные контракты. Не подключать торговые ключи к общему frontend deployment.
