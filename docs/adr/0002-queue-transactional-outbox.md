# ADR-0002. Очередь — transactional outbox в той же БД

Статус: **принято**.

## Контекст

ТЗ требует, чтобы событие, переход состояния и будущая команда записывались одной транзакцией (02 §8, шаг 1), чтобы повторная доставка считалась нормальной (EX-040), а денежная команда после возможного внешнего эффекта не повторялась автоматически (02 §8, EC-016, EC-017).

## Решение

1. Команды — строки `command_outbox` в БД обмена, создаются в той же транзакции, что и переход состояния сделки. Входящие события провайдеров — `provider_event_inbox` с дедупликацией.
2. Worker забирает команду через `SELECT … FOR UPDATE SKIP LOCKED` и получает lease с монотонным fencing token.
3. Ключ команды — устойчивый business action ID по сделке и конкретному обязательству (EC-016), `payloadHash` неизменяем.
4. Для браузерных действий фиксируются `PREPARED → ATTEMPT_STARTED → RESULT_CONFIRMED | UNKNOWN_RESULT`; `ATTEMPT_STARTED` коммитится до клика (EC-017).
5. Автоматический повтор разрешён только для команд без денежного эффекта. Денежная команда после `ATTEMPT_STARTED` повторяется только по доказанному отсутствию эффекта (02 §8, шаг 7).
6. Пробуждение — опрос с коротким интервалом; `LISTEN/NOTIFY` допустим как ускорение, но не как единственный механизм.

## Почему не Redis/BullMQ и не готовые очереди на Postgres

- Redis/BullMQ: постановка в очередь не атомарна с транзакцией состояния, а встроенные повторы противоречат правилу `UNKNOWN_RESULT`. Понадобился бы outbox всё равно, плюс ещё одна система с состоянием.
- pg-boss, graphile-worker: атомарность достижима, но состояния попыток браузерного действия и правило передачи владения профилем (EC-014) всё равно свои, и таблицы задвоились бы. Можно вернуться к ним для неденежных задач, например доставки промо.

## Последствия

- Нагрузка очереди ложится на Postgres; при объёмах этапа (1 одновременный заказ на профиль, EC-023) это несущественно.
- Fencing token защищает только БД. Остановку прежнего браузерного процесса доказывает супервизор профиля (EC-014, T3.3), а не lease.
