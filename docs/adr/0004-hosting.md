# ADR-0004. Хостинг исполнителей

Статус: **принято** 29.10.2026: VPS Hetzner. Условие про размещение браузерных исполнителей — ниже, в «Что проверить на этапе A».

## Решение

VPS Hetzner Cloud, Ubuntu 24.04, Docker Compose. Деплой — из workflow `image` через GitHub Environment `production` с обязательным подтверждением; на сервере `deploy/remote-deploy.sh` с проверкой здоровья и откатом. Подготовка сервера — `deploy/bootstrap-server.sh`, порядок — [deploy/README.md](../../deploy/README.md).

На первом шаге на сервере только `exchange-api` на `127.0.0.1`; наружу открыт только SSH. БД появляется к G1 (ADR-0001: на этом же сервере с внешними бэкапами или управляемый Postgres в том же регионе), браузерные исполнители — на этапе C.

## Требования ТЗ

- Браузерные исполнители — постоянные процессы с устойчивым профилем, не serverless (07 §2, EX-040). Vercel для них не подходит.
- Отдельные сессии Walt и Ощада, один активный исполнитель на профиль (EC-014), параллельность на сессию Ощада — 1 (06 §3).
- Профиль, cookies и storage state не попадают в git, frontend и логи (07 §2).
- Секреты только на сервере в защищённом хранилище, с ротацией (02 §13).

## Предлагаемая форма

1. Отдельные контейнеры: `exchange-api`, `exchange-worker`, `walt-browser-worker`, `oschad-browser-worker`. Профили браузеров — на отдельных зашифрованных томах, доступных только своему контейнеру.
2. Исходящий трафик браузерных контейнеров ограничен разрешёнными доменами, которые фиксирует этап A.
3. `exchange-api` слушает loopback; наружу — через обратный прокси с mTLS или HMAC только для серверной части `raffle-admin-next` и для сборщика push.
4. Секреты — менеджер секретов провайдера или sops+age; `.env` на сервере только как точка монтирования, не в репозитории.
5. Ежедневный бэкап БД и учение по восстановлению по правилу 02 §12 (R-10).

## Что проверить на этапе A до выбора площадки

Hetzner размещает серверы в Германии, Финляндии, США и Сингапуре, то есть сессии Ощада и Walt пойдут с адреса дата-центра в ЕС. Как кабинет Ощада и Walt на это реагируют, проверяется на этапе A до переноса браузерных исполнителей на сервер. Если штатный вход оттуда не работает, исполнители размещаются там, где он работает (например, выделенный компьютер у оператора), а API, worker и БД остаются на Hetzner. Прокси и подмена адреса для обхода защит банка или Walt не применяются (EX-008, 06 §2).

## Варианты

| Вариант | Плюсы | Риски |
|---|---|---|
| VPS в Украине | Привычная для банка география | Устойчивость площадки, требования к резервированию |
| VPS в ЕС | Надёжность, управляемые сервисы рядом | Возможные проверки безопасности банка при входе |
| Выделенный компьютер у оператора | Сессии с обычного адреса, физический контроль | Питание, сеть, физическая безопасность, резервирование |
